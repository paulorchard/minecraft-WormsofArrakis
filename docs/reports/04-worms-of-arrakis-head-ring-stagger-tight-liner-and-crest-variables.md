# Report — Prompt 04 Worms of Arrakis: head as one ring, staggered scales, tight liner, base level and crest variables
Status: partly (Parts 0-5 built, unit tested, one dedicated-server smoke start, jar deployed; nothing seen on screen because no client was run; `surface world` untouched and untested)   Commit / tag: base-1, head-1, liner-1, stagger-1, crest-1, frame-1 (one commit, because all six parts share the same skin and path code)

## What was built
- Part 0 (base-1): `path/WorldBase` with `BASE_Y = 63` ("the Minecraft sea level, the base of the sand; every height in the worm code is relative to it"), `resolve(seaLevel, feetY)`, and the command `/arrakis_worm_test base <y|here|sea>` (default sea). Moves are spawned with the entity origin at the base level, so the engine stays at local y = 0 and the renderer needs no translation (path y = world y - base y holds by construction). Log: `[WormsOfArrakis] base level: y=...` at the command and at every move spawn.
- Part 1 (head-1): the head is segment 0 of the chain, built by the same `ShingleMath` path as every other ring. The rigid frustum body and `HeadSpec.BODY_LENGTH` are gone for moves (the prompt 01 `mouth` command keeps its own experiment model, with the constants moved into `MouthModel`). New `geometry/HeadFlaps`: three flaps hinged on the ring's front-edge skin vertices; `WormSkin` adds them when segment 0 is built. `HeadSpec.headLength(width)` = pitch + `CONE_HEIGHT` x R. The move renderer draws everything as skin geometry; the GeckoLib model of a move is empty.
- Part 2 (liner-1): per ring, the liner radius is the deepest plate, lip or rim vertex radius of that ring minus `liner_margin` (0.02), and the smaller of the two neighbours at a joint. The 0.25 floor is removed.
- Part 3 (stagger-1): `geometry/Stagger` (seeded hash, ring offsets, tile orientations, jitter). `ShingleMath.Options.withVariety(stagger, seed, tiles, jitter)`; per-quad colour is stored in `Result.color`. Commands `stagger <fraction|off> [seed]`, `jitter <0..0.1>`, `tiles on|off`. Defaults in the test commands: stagger 1.0, jitter 0.04, tiles on. `Options.defaults(...)` itself stays plain (stagger 0, no tiles, no jitter) so the maths tests of prompts 02 and 03 are unchanged.
- Part 4 (crest-1): `crest <width> <segments> [height=0.4] [radius=6] [radius_down=<radius>] [speed=12] [force]`, keyed in any order; a bare number is read as height (a second bare number as speed, as in the old syntax). Height maximum 3.0 body widths.
- Part 5 (frame-1): `freeze <t|off>` and a frame line per frame (`frame t=...: headTipHeight=...W headHeading=...deg headDx=...W exposedRings=...`) at spawn (t = 0, 1/3, 2/3, 1) and at each freeze.
- Jar: `IslandCraft-WormsOfArrakis-0.1.0.jar` (in the ArrakisTest01 `mods` folder; older jar deleted; GeckoLib 5.5.3 there; GeckoMesh stays `.disabled`; no PNG in the jar).

## Answers to the prompt's questions
1. Base level: the sea level read from the game is `-63` in the smoke run's flat dev world (`ServerLevel.getSeaLevel()`); a normal overworld reports 63 (not checked in this run). `BASE_Y = 63` lives in `path/WorldBase` as the fallback. `base here` sets the base to the player's feet Y minus 1 (taken literally: standing on a block whose top is at Y = 64.0, feet are 64.0, base is 63.0), `base <number>` a fixed Y, `base sea` the level's sea level. The move entity is spawned with its origin at that Y, so local y = 0 is the base everywhere; the worm is placed in front of the player (as before), not on the player's x and z, so the player is not inside it.
2. Head ring: segment 0 is built by `ShingleMath` like every ring. The n front-edge skin vertices (`ShingleMath.frontVertex`, the same function the plates use, with the ring's stagger turn) are the flap hinge vertices; the flaps split them into three arcs sharing their end vertices (faces 4/3/3 for n = 10, 17/17/16 for n = 50, 50/50/50 for n = 150). Each flap is a fan of triangles from its hinge arc to the apex on the axis (cone height 0.6 R); open, the apex swings outward about the chord through the two hinge arc ends (70 degrees by default), the arc's interior vertices stay on the ring. Both faces are drawn (the inside is tinted like the liner); the texture is the dripstone by reference. HEAD_LENGTH = pitch + 0.6 R: width 3 = 1.00 + 0.97 = 1.97; width 16 = 1.00 + 4.78 = 5.78; width 48 = 1.00 + 14.32 = 15.32. Emerge n: n body rings above the base level, the head ring and flaps on top. Base height (rear of the head ring) = n sin(angle); top of the flaps = (n + HEAD_LENGTH) sin(angle). For W16, n = 10, 90 degrees: 10.00 and 15.78 (was 10.00 and 22.78 with the rigid 8-block head; the stop rule is now "exactly n body rings above the base", so the old n counted the head ring too). Crash: `maxExposed` and the `exposed` fields now count body rings, and the minimum worm length rose by one ring (101 segments for `crash 16 80 10`).
3. Liner: the real inset below the skin surface is 0.122 for a straight chain at widths 16 and 48; at the 2-widths limit it is 0.122 on the straight rings and up to 0.288 at the most open joint (all planes, widths 16 and 48). The expected 0.12 held. Seam test (`skinIsWatertightAroundEveryRing`): passed for widths 16 and 48, yaw / pitch / diagonal at the limit, stagger 0 and 1.0: the two lengthwise edge vertices of every skin face are bit-identical to those of the next face of the same ring (the faces share the same vertex arrays). So the slits the owner saw are the depth between plate and liner, which the tight liner reduces; nothing needed fixing in the skin.
4. Stagger: the lip is computed against the neighbour ring's real surface: for each vertex of ring k-1 at local angle a, the gap is measured against the point of ring k's polygon at the same angle, found on its face edge (radius = R cos(pi/n) / cos(t - pi/n) with t the angle inside the face). With equal rotations this equals the old vertex-to-vertex gap. The seed is a long: `stagger <fraction|off> <seed>` or, by default, the entity id; every value is a hash of (seed, fixed ring index, face index, purpose), never of position. Ring offsets: ring 0 is hashed, every next ring steps by 0.15 to 0.85 of a face from the one before (mod 1), so neighbouring rings differ by at least 0.15 of a face (independent uniform offsets could only promise 80% of pairs over 0.1, below the required 90%; the stepped version gives 100%). Statistics: for seeds 1, 2, 3, 12345, 99999 in a 100-ring worm, 99 of 99 pairs differ by more than 0.1 of a face. Build time (whole worm, 100 segments, stagger + tiles + jitter): width 16: 3.8 ms for 25,000 quads (plain 3.5 ms); width 48: 12.9 ms for 75,000 quads (plain 12.8 ms); the stats cache still builds a static pose once (cache key includes the visual switches).
5. Crest: apex top against height (path, plates in brackets for widths 3 and 16): at width 16, height 0.2 / 0.4 / 0.8 / 1.3 / 2.0 / 3.0 gives 3.2 / 6.4 / 12.8 / 20.8 / 32.0 / 48.0 (the plates measured 20.800 for 1.3); at width 3: 0.600 (0.599), 1.200 (1.198), 2.400 (2.398), 3.900 (3.897), 6.000 (5.999), 9.000 (8.999); width 48 gives exactly height x 48. `crest 16 80 height=1.3 radius=6`: entryAngle 9.8, exitAngle 9.8, span 146.5 blocks (9.2 W), exposedLength 153.6 blocks (9.6 W), apexTop 20.80. `crest 48 60 height=1.3 radius=6`: entry 5.7, exit 5.7, span 470.1 (9.8 W), exposedLength 490.4 (10.2 W). (The 48-wide numbers are from the 60-segment test move; the arch does not depend on the segment count.) Against the reference diagram (top 1.3 W, about 8 W long, gentle, head dives at about 30 degrees): the height matches by definition and the length is 9.6 W against about 8 W (the arch is measured where the body top crosses the base level; with radius_down=3 it is 8.2 W, with radius=5 both sides about 8 W). The dive angle does not match: at radius 6 the body top crosses at 9.8 degrees, the head tip itself at about 26 degrees where it rises through the base level (frame t = 0 reads 26 and -26). A 30-degree dive of the body needs a much tighter descent: `radius_down=2` gives an exit of 17.0 degrees (3: 13.9, 4: 12.0, 6: 9.8), so the diagram's 30 degrees is a head dive rather than the body crossing, or needs a radius below 2 widths (force). Use `radius_down` to match the picture by eye.
6. Frames: `crash 16 150 25` (default angle 70), measured against the reference (head tip height in W, heading, dx in W): frame 1 (t = 0.33): 2.75 W, +20 degrees, 1.74 W, against 2.5 W, about +85, 0; frame 2 (t = 0.67): 2.68 W, -25 degrees, 3.29 W, against 2.0 W, -15, 2.3; frame 3 (t = 1.00): -0.00 W (head back at the base), -70 degrees, 4.87 W, against 1.5 W, -30, 4.3; the reference's fourth frame (0.4 W, -80, 7.1 W) has no match because the table ends when the tip is back at the base. Also measured at angle 45: 1.71 W / 13 / 2.09, 1.63 / -21 / 3.27, -0.00 / -45 / 5.13; at angle 85: 3.29 / 24 / 1.29, 3.24 / -28 / 3.08, -0.00 / -85 / 4.27. The strip is not the same set of moments as my table, so the comparison is by shape: the real crash is higher at the top than the reference (about 2.7 W against 2.0 to 2.5 W) and its head is near-vertical only at entry and exit (the arc over the top has radius 2 W, the limit), nose down at -70 only when it re-enters; the reference's "-80 at 0.4 W" fits `angle=85` re-entry, and its 7.1 W of horizontal travel is more than any setting here (4.3 to 5.1 W): the knob that stretches it is the arc radius over the top, which is fixed at the 2-width limit in this prompt (a `top_radius` option exists in the spec but is not on the command line). The knob that moves the height is `n` (the point where the head turns); `angle` moves the entry and exit headings.
7. Blockers for the next prompt: none in the geometry. Sand displacement and particles need the two path crossings (`Move.sCross1`, `sCross2`, `path.pos`) and the head's crossing times, which the frame code already finds. Spawning and breach location need only a `SurfaceProvider` (the world one exists and compiles) and a choice of the entity origin; the move already starts at its own base level. The mouth rework only touches `HeadSpec` and `HeadFlaps`. Peristaltic crawling needs a new s-to-time script; the pose stays a function of the head s.

## Surprises, problems, deviations from the prompt
- The sea level of the dev server's flat world is -63, not 63. `base sea` follows the level, so in that world it puts the worm at Y = -63; the constant 63 is the fallback only.
- The worm is placed in front of the player, as in prompt 03, not at the player's x and z; the move's zero is at the base level instead.
- "Neighbouring rings differ by more than 0.1 of a face for at least 90% of the pairs" cannot be met by independent random offsets (80%); the ring offsets are therefore stepped from the previous ring (still a pure function of seed and ring index).
- Prompt 03's numbers change with the new head: the old n counted the head body; the base height is n sin(angle) as before, but the mouth top is lower (15.78 at W16 instead of 22.78) because the head is now one ring plus the 4.78 flaps. Tests of prompt 03 (exposed count, head tip on the path, crest ceiling of 0.5) were updated for this, not weakened: the tip-on-path tolerance is now 0.05 W + 0.1, because the flap tip lies on the tangent, not on the curved path (prompt 03's tip lay exactly on the path because the head was a chord).
- Mouth open/closed is a fixed angle (static); the old animation is not used by the flaps.
- The first crest example numbers of prompt 03 (`crest 16 60`, fraction 0.4) are the same as `crest 16 60 height=0.4` with `radius=2` (the old arch radius was the 2-width limit); the default radius is now 6, so a bare `crest 16 60` is a flatter, longer hump than in prompt 03. `radius=2` brings the old shape back.
- The frame table is measured between the head tip rising above the base and falling back below it; for emerge the head does not move horizontally, so dx is 0.
- Commands `freeze` and `speed` found 0 worms in the server-console smoke run (no loaded chunk at the spawn point); they work through the same spec-string mechanism as prompt 03's `speed`.
